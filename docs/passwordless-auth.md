# Google registration, email OTP, and portal password login

/register is Google-only. For ordinary CSU accounts, /login sends an email code using sendLearnerOtp in src/services/learnerOtp.js. It calls signInWithOtp with shouldCreateUser: false and no redirect option. verifyLearnerOtp calls verifyOtp with type: 'email' and requires a matching session. The exact addresses admin@carsu.edu.ph and osas@carsu.edu.ph instead use Supabase password sign-in; no OTP bypass or mock session is used. Password sign-in is only offered for those addresses, and all authenticated accounts still require an active public.users profile and the matching active user_roles entry before entering a portal.

Supabase performs the registered-account check; the frontend does not query public users by email. Some server configurations deliberately hide whether an account exists. A generic response is not proof of registration; login never enables account creation.

AuthProvider restores and observes the shared Supabase session. Protected routes require an active public.users profile and active user_roles entry. Admin and OSAS are exclusive portal destinations when either privileged role is active: Admin goes to /admin-dashboard, OSAS goes to /osas-dashboard, and they cannot enter Learner/Tutor routes even if those roles are also assigned. Other accounts default to Learner when available; Tutor-only accounts reach Tutor. Google returns to /register and then the appropriate role dashboard. Logout signs out through Supabase. Learner/Tutor local drafts are scoped to the user ID. Existing server RLS must enforce all permissions independently of UI guards.

## Required learner profile setup

Before using the profile form, review and manually run `supabase/manual/learner_profile_setup.sql`. It adds `short_bio`, `study_interests`, and `student_id_image_path` to `public.users`, updates the `complete_learner_profile(details jsonb)` RPC, makes the existing `student-id` bucket private, and installs owner-folder Storage policies. It does not create a bucket. The RPC only updates the authenticated active learner, checks verified CSU email and required fields, verifies that an onboarding image exists in the authenticated user's bucket folder, and cannot edit email, role, or account status. No SQL was executed automatically.

Incomplete learner accounts (including existing accounts missing these fields) see a required popup. Dashboard, Settings, Help & Support, and Logout remain available; other navigation items stay visible and locked. The shared popup can be closed without unlocking restricted sections and reopened with Complete Profile. Successful saving reloads the database profile and unlocks the requested dashboard. Completion is derived from saved fields, not browser storage. Full name is stored using the existing first_name/last_name columns by splitting at the first space.

The gate is an interface restriction. Any future server booking/messaging mutations must enforce profile completeness in their own RPC/RLS policies as well. Existing non-learner staff roles are not subject to learner onboarding.

## Student ID images during initial profile setup

The initial setup form accepts separate front/back JPEG, PNG or WebP images (10 MiB each). The profile fields stay hidden until the student attempts extraction. Extract ID Details starts the existing browser-side Tesseract OCR. After an attempt, extracted values are read-only by default; the student must click **Allow Edit Details** before correcting them. The front/back raw-text panels are not shown. College/Program values use the centralized dependent dropdowns; OCR failure on a field does not force a rescan. There is no manual-entry bypass before attempting extraction. OCR does not verify identity or ID authenticity. Year level, phone, bio and interests stay manual. Email comes from the authenticated CARSU account.

Save and Continue appears only after extraction, image selection, review confirmation, and validation of all required fields. It uploads the original front image used for OCR to the existing private `student-id` bucket, then saves the profile and Storage path through `complete_learner_profile`. The path is `<auth.users.id>/<sanitized full name>/student-id.<jpg|png|webp>`; the first segment is the security boundary, while the readable name is organizational only. Uploads use upsert at that stable path, so retrying the same save does not create duplicate objects. If the database save fails, a newly uploaded object is removed when possible and the profile gate remains open. Temporary preview URLs and OCR text are never saved. Closing the modal discards the selected files and review state; the profile is not marked complete until the RPC succeeds. Existing complete profiles do not have to repeat onboarding; legacy complete profiles without an image path remain editable.

Keep the `student-id` bucket private. The setup SQL grants authenticated users read/insert/update/delete only under their own `{auth.uid()}/...` folder; review existing permissive Storage policies as they can still broaden access. Do not add public access or service-role credentials to the frontend. The OCR review gate is a UI workflow, not a server identity-verification control.

## Tutor application document storage

Tutor application documents are uploaded to the existing private `apply-as-tutor` bucket as they are selected. Paths use `<auth.users.id>/<sanitized-full-name>/<document-type>-<unique-id>-<sanitized-filename>.<extension>`; the user ID is the ownership boundary and the name is only for readable organization. Each new upload gets a unique path so an unsubmitted replacement cannot overwrite a document already attached to a saved application. Replaced documents are removed after the new application is saved; unsubmitted uploads are removed when the applicant exits the form. Application details and document references are submitted to `public.tutor_applications` and `public.verification_documents` through a database RPC; drafts are no longer saved in browser storage. Legacy browser-only application metadata and IndexedDB files are removed when the application screen loads. Applicants can access their own files; active admins can review application files.

Before enabling applications, confirm that the `apply-as-tutor` bucket already exists, then review and run `supabase/manual/tutor_application_storage.sql` followed by `supabase/manual/tutor_application_backend.sql` in the Supabase SQL Editor. The storage migration keeps the bucket private, applies the form's 10 MiB/PDF/JPEG/PNG limits, and adds owner-folder policies plus active-admin reads. The backend migration adds application details/history and document metadata columns to the supplied tables, restricts direct writes, and installs applicant-submission and admin-review RPCs. The submission RPC verifies the active learner and confirmed CSU session, validates the application and required files, and checks that document objects exist before saving. Admin approval creates or updates the tutor profile and activates the tutor role. These migrations were prepared locally and have not been run against the project. Review existing `storage.objects` policies because permissive policies are additive. No service-role key is used by the browser.

Applications cannot be submitted or reviewed until both migrations have been applied to the connected Supabase project. If submission fails, the UI displays the backend error instead of reporting a local save.

## Tutor credential OCR and RegEx-assisted checks

In Admin > Tutor Verification, choose **Run All Document Checks** once to analyze every uploaded application document in sequence. The Admin browser downloads each private Storage object through the authenticated Supabase client. Image inputs are resized for OCR, converted to grayscale with contrast enhancement, and passed to the existing local Tesseract.js English worker with automatic orientation correction. PDFs are opened in the browser using PDF.js: selectable embedded text is extracted directly; scanned pages are rendered at high resolution, enhanced, and passed to Tesseract with automatic orientation correction. At most the first eight PDF pages are processed, and a longer file is explicitly marked as truncated for manual review. Results and failed checks are shown below each document. Extracted OCR text is not displayed or saved, and is not uploaded to an OCR service.

RegEx and normalized-text checks look for a likely student ID (`3–4 digits`, hyphen, `4–8 digits`), compare it with the applicant profile, look for the applicant's name, and check document-specific CSU wording and layout. COR checks recognize Caraga State University, Certificate of Registration/enrollment wording, and expected student/program/academic-year/semester/subject or unit fields. Grade evidence checks recognize the CSU Student Grade Report or Evaluation of Grades title, expected subject/description/grade/completion/unit table headings, and grade values (`1.00`–`5.00` in quarter increments, `PASSED`, `INC`, `DRP`, or `W`). A detected mismatch is surfaced; uncertain or unreadable fields are marked for manual review. OCR and pattern matches are only decision support: they do not authenticate a document, verify its issuer, or approve/reject an application. Admins must inspect the original document and make the final decision. Analysis is transient in the review UI and is not saved to the database.

PDF.js is loaded only when an Admin runs OCR on a PDF. Password-protected or unsupported PDFs, OCR failures, and pages beyond the eight-page limit require manual review.

The Profile screen uses saved account values instead of placeholder identity/academic text. Its editable sections save through the existing profile RPC and reload the Supabase profile.

## CSU college/program catalogue

`src/data/collegeProgramMap.js` is the single source of truth, based on the supplied project catalogue (including majors/departments and AY 2026-2027 Architecture/Mechanical Engineering). The setup form shows full names in College and dependent Program selects; changing College clears Program. Internal codes remain in the catalogue/OCR result; existing users.college and users.program columns store canonical names. The only added database column for this flow is `users.student_id_image_path`.

OCR recognizes bounded codes and full names, separators/case/spacing, and limited I/1 or O/0 substitutions. A unique program can identify its college; conflicting/multiple detected colleges or programs yield no academic suggestion. Student-ID detection supports the supplied 231-01293 format and older four-digit-prefix IDs. Existing nonempty/length/uniqueness validation remains; no universal student-ID format is invented. Names remain reviewable.
